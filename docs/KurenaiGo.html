KurenaiGo ドキュメント

KurenaiGoは、KurenaiEngine (KurenaiEngine2D)で描画し、KataGo をGTP経由の対局相手として使う囲碁(Go)アプリです。このドキュメントでは、アプリ本体 (KurenaiGo/Source/以下)の実装内容を説明します。KurenaiEngine自体のAPIリファレンスは KurenaiEngine/docs/KurenaiEngine.html を参照してください。

1. 現在の実装範囲KataGoとの対局・解析表示が可能

盤の大きさの選択(9路/13路/19路、10.5節参照)、マウスでの着手、合法手判定・捕獲・シンプルコウを 含むルール、そしてKataGoをGTP(Go Text Protocol)経由の子プロセスとして起動しての対局(人間=黒、KataGo=白)までを実装しています。あわせて、 kata-analyzeによる局面解析を使った勝率表示・地合い可視化・着手ヒント(8章)、 棋譜(SGF)の自動保存・再生・再生中の解析表示と損失グラフ(9章)、レート戦/カジュアルの 対局モード分けと棋力の数値化(レーティング、盤の大きさごとに別々に記録、10章)、レーティングに 応じたAIの強さの自動調整(11章)、レート戦終了時の自動解析による苦手分野の解析(局面ごとの 悪手率、12章)も実装済みです。色の選択・ハンディキャップは未実装です(13章参照)。

2. 座標系とレイアウト

KurenaiEngine2Dのワールド座標はウィンドウのピクセル座標そのもので、原点は画面左下、 Y-upです(DrawSpriteのx, yはスプライト中心)。KurenaiGoではウィンドウの リサイズに追従できるよう、毎フレーム renderer.GetWidth()/GetHeight() から 盤のレイアウトを再計算しています(ComputeBoardLayout)。盤の目の数(boardSize、 9/13/19のいずれか、10.5節参照)も引数として渡し、LineSpacingの分母に使うことで、 盤の一辺の物理サイズは変えずに目の間隔だけを盤の大きさに応じて変えています。 

struct BoardLayout
{
    float CenterX;      // 盤の中心(ウィンドウ中心)
    float CenterY;
    float BoardExtent;  // 木目の盤面の一辺の長さ
    float GridExtent;   // 格子線が占める範囲の一辺の長さ(盤面より内側)
    float LineSpacing;  // 目の間隔 = GridExtent / (boardSize - 1)
};
  • BoardExtentはウィンドウの短辺 × kBoardExtentRatio(0.88)。 常に正方形になるよう短辺基準で計算する。
  • GridExtentはBoardExtent × kGridExtentRatio(0.90)。 盤面の外周に木目の縁が見えるよう、格子線の範囲を一回り小さくしている。
  • 格子線のインデックス(0〜boardSize-1)からワールド座標への変換は GridIndexToCoordinateが行う(中心からGridExtentの半分だけ引いた位置を 起点に、LineSpacing刻みで並べる)。

3. 盤・石の描画

盤面(木目)はCreateSolidColorTexture(255, 255, 255, 255)で作成した白1色のテクスチャを 木目色でティントした矩形スプライトで描画します。格子線・星・石はいずれも KurenaiEngine2D::DrawLine/DrawCircleで直接描画しており、円形テクスチャを 事前生成する必要はありません(かつてはTools/generate_stone_textures.ps1で石の PNGを生成していましたが、DrawCircleの追加に伴い削除しました)。

3.1 効果音

着手時(人間・KataGo双方)にstone_place.wav、対局終了(投了・両者パス後の final_score)にgame_end.wavをKurenaiEngineBase::PlaySoundで再生します。 いずれも実際の録音ではなく、Tools/generate_sound_effects.ps1で正弦波を合成して 生成した16bit PCMのWAVファイルです(Assets/Sounds/にコミット)。

4. ルールエンジン(GoBoard)

KurenaiGo::GoBoard(Source/GoBoard.h/.cpp)は盤面と囲碁のルールのみを 扱う、描画・入力から独立したクラスです。座標はrow=0が盤の下端・col=0が 左端(row*Size+colの1次元配列)で、これは2章のワールド座標系(インデックス0が下/左) およびGTPの座標系(行1=下端、列A=左端)の両方と一致するため、変換が単純になります。

4.1 合法手判定と捕獲

TryPlay(row, col, color)は次の順序で処理します。

  1. 空点でなければ非合法。シンプルコウで禁止されている地点なら非合法。
  2. 石を仮に置き、隣接する相手グループをフラッドフィル(CollectGroup)で走査して 呼吸点(liberty)を数える。呼吸点0のグループがあれば取り上げる(複数方向から同じグループに 到達する場合の重複除去あり)。
  3. 相手を取り上げた後、自分のグループの呼吸点を再計算する。0なら自殺手として非合法・ 全ての変更をロールバックする。
  4. 合法なら確定し、連続パス数を0にリセットする。取り上げた石の数はその色のアゲハマ (CapturesBy)に加算する(自殺手としてロールバックする場合は加算しない)。

4.2 シンプルコウ

直前の手が「相手をちょうど1つ取り、打った石自身が呼吸点1つ(その取った地点)だけの単独石になる」 形だった場合、その地点への即座の再着手を次の1手だけ禁止します(m_KoForbiddenIndex)。 パスを含むいずれかの着手が行われるとこの制約は解除されます。より厳密な超劫(局面の反復)判定は 行っておらず、一般的なアプリで広く使われる簡易版のコウ規則です。

4.3 地の計算をしない理由

GoBoard自体は地の計算(スコアリング)を行いません。生きた石・死んだ石の判定 (セキ等の特殊な形を含む)を自前実装するのは複雑で誤りやすいため、対局終了(両者パス)時は KataGoのfinal_score(7章)にスコアリングを委譲しています。

5. マウス・キーボード入力

KurenaiEngineBaseが公開するウィンドウスコープの入力API(IsMouseOverWindow・ WasMouseButtonPressed・WasKeyPressed・GetClientMousePosition)を 使っています。これらはウィンドウメッセージ(WM_MOUSEMOVE/WM_LBUTTONDOWN/ WM_KEYDOWN等)から状態を更新するため、GetAsyncKeyState/GetCursorPosと 異なりウィンドウがフォーカスを失っていれば反応しません。かつて必要だった、自ウィンドウのHWNDを FindWindowW(L"KurenaiEngineWindowClass", ...)で検索する回避策も、GetWindowHandleを 含むこれらのAPIが揃ったことで不要になりました。

GetClientMousePosition()はWin32標準のクライアント座標(原点は左上、Y-down)を返すため、 height - clientYでワールド座標(原点は左下、Y-up)に変換します。最も近い交点との距離が LineSpacingの40%以内であればその交点を「ホバー中」とみなします (TryGetHoveredIntersection)。クリック・パス・投了・地合い表示切替(T)・ 着手ヒント表示切替(H)はWasMouseButtonPressed/WasKeyPressedが すでに「直前のPumpEvents()呼び出し中に押された」立ち上がりエッジを返すため、 KurenaiGo側で前フレームとの比較を自前実装する必要はありません。

自動検証時の注意: IsMouseOverWindowは内部でTrackMouseEvent (TME_LEAVE)を使っており、これは実際のカーソル位置も見ています。PostMessageで WM_MOUSEMOVEを送ってウィンドウ内へカーソルがあるように見せかけても、実カーソルが ウィンドウ外にあると直後にWM_MOUSELEAVEが発生しIsMouseOverWindowが falseに戻ってしまう(ホバー判定だけが効かなくなる)ことを実機検証で確認しました。ホバー判定を 含めてPostMessageで動作確認したい場合は、実カーソルも対象ウィンドウのクライアント領域内に 置いた状態で行う必要があります。ボタン押下・キー入力自体(WasMouseButtonPressed/ WasKeyPressed)はこの制約を受けず、実カーソル位置に関係なくPostMessage/ SendMessageだけで正しく検証できます。

現在のTurnStateとアゲハマ数(GoBoard::CapturesBy)は、盤の下マージンに DrawTextで常時表示します(DrawHud、BuildStatusText)。 DrawTextはかな漢字を含むUnicode文字に対応しているため、表示文言は日本語です。 対局終了・投了・通信エラーのような割り込みが必要な通知は、既存のエラーダイアログのまま 残しています(進行中の状態はHUD、区切りとなるイベントはダイアログという役割分担)。

文字化けの修正: 本プロジェクトは/utf-8オプションでコンパイルしており、 ナロー文字列リテラル("...")はUTF-8でエンコードされる。これをMessageBoxAに そのまま渡すと、ANSI版はシステムのコードページ(日本語環境では多くの場合Shift-JIS)で解釈するため 日本語部分が文字化けする。Main.cppのShowMessageBoxUtf8で MultiByteToWideChar(CP_UTF8, ...)によりUTF-16へ変換してからMessageBoxWへ 渡すことでこれを解消している。KataGoClientの例外メッセージ(LastError())や std::exception::what()も同様にUTF-8として扱われるため、すべての通知はこのヘルパー 経由で表示している。

owner未指定のMessageBoxWは閉じた後のフォーカスの戻り先が不定になる(実機で検証): ShowMessageBoxUtf8は元々すべての呼び出しでownerにnullptrを 渡していたが、この場合ダイアログは所有者を持たない独立したトップレベルウィンドウになり、閉じた後に キーボードフォーカスがメインウィンドウへ確実に戻る保証が無いことを実機検証で確認した (PostMessageで送ったWM_KEYDOWN/WM_KEYUPがメインウィンドウの ウィンドウプロシージャには届くものの、キー入力状態としては一切反映されなくなる現象として現れる)。 11章のAI強さ設定機能の実装中、対局モード選択の直後にキー入力を受け付ける必要があるテストで発覚した。 ShowMessageBoxUtf8にHWND owner引数を追加し、メインループ内の呼び出し箇所は すべてrenderer.GetWindowHandle()を渡すよう修正した(アプリ全体の既存のダイアログにも 同じ問題があった可能性があり、あわせて修正している)。唯一、wWinMain最外周の致命的 エラーハンドラ(renderer自体の構築に失敗した場合にも実行され得る)だけは rendererが有効とは限らないためnullptrのままとしている。

7. KataGo連携(KataGoClient)

KurenaiGo::KataGoClient(Source/KataGoClient.h/.cpp)は katago.exeをgtp -model <model.bin.gz> -config <gtp.cfg>で 子プロセス起動し、標準入出力を匿名パイプでリダイレクトしてGTPのテキストコマンド/応答を やり取りします(CreateProcessW + CreatePipeによるWin32の標準的な 「リダイレクトされた入出力を持つ子プロセス」の実装)。標準エラー出力(チューニング進捗等の 診断ログ)はKataGo/katago_stderr.logへリダイレクトしています。

7.1 非同期処理

起動処理(StartAsync)とKataGoの着手要求(RequestGenMove)・終局判定 (RequestFinalScore)は、OpenCLの初回チューニング(数十秒)やKataGoの思考時間 (time_settings 0 5 1で最大5秒/手)がかかるため、いずれも専用スレッドで実行します。 メインの描画ループはTryGetGenMoveResult等のポーリングで結果を受け取るだけなので、 KataGoが応答を返すまでの間もウィンドウは応答なしにならず、盤面の再描画・リサイズ処理を続けられます。

7.2 座標変換

GTPの座標は列がA〜T(Iを除く)、行が盤の下端から1始まりの数字です。 GoBoardの座標系(row=0が下端、col=0が左端)と対応しているため、 ToVertex/ParseVertexでの変換は「列インデックスに応じてAから 数え上げ、Iをまたぐ場合は1つ増やす」「行はインデックス+1」という単純な計算のみで 行っています。

7.3 GTPコマンド

コマンド用途

7.4 終了処理

KataGoClientのデストラクタは、進行中のワーカースレッドの完了を待ってから quitを送信し、プロセス終了を最大3秒待って、それでも終了しない場合は TerminateProcessで強制終了します。これによりKurenaiGoを閉じてもkatago.exeが 残留しません。

8. 解析結果の可視化(勝率・地合い・着手ヒント)

黒(人間)の手番になるたびにKataGoClient::RequestAnalysis(Stone::Black)で kata-analyzeによる局面解析を要求し、結果をDrawWinrateBar (勝率バー)・DrawTerritoryOverlay(地合い可視化、Tキーでトグル)・ DrawMoveHints(着手ヒント、Hキーでトグル)の3つの描画関数で 可視化しています。KurenaiEngine2Dには文字描画機能が無いため、勝率は数値では なく黒/白の面積比を表す横棒、地合いは色つきの半透明オーバーレイ、ヒントは順位別に色分けした マーカーとして、すべて既存のDrawSprite(矩形スプライト)のみで表現しており、 この機能のためにエンジン(KurenaiEngineサブモジュール)側の変更は行っていません。

8.1 kata-analyzeのプロトコル(実機で検証)

kata-analyze <B|W> interval 50 ownership trueを送ると、GTPの即時応答 (= )は返らず、代わりにinfo move <頂点> visits N ... winrate W ... scoreLead S ... order K ... pv ... [次のinfo move...] ownership <361個の浮動小数> という1行の報告が定期的に再送され続けます(差分ではなく毎回全体を送り直す)。 winrate/scoreLead/ownershipはいずれも コマンド引数で指定した色(手番側)から見た値で、order 0の 候補手が最有力手(=現局面の評価値として使う値)です。ownership配列(19路なら 361要素)は盤面左上(GTPのA19)がindex 0で、右→下へ行優先(row-major)に 並びます。KurenaiGoの内部座標(row=0が盤面下端・col=0が左端)に 対応させると ownershipIndex = (Size - 1 - row) * Size + col となります (黒石をA19に置いて解析し、index 0付近の値が最も強く反応することを確認して検証済み)。

解析の停止方法に関する既知の癖: kata-analyzeは一般的には空行を送ると 停止しますが、このKataGoビルドでは「報告を受け取ってから短時間で空行による停止要求を送ると、 その後の応答が返らなくなる(ハングする)」現象を実機で複数回確認しました。空行の代わりに 通常のGTPコマンド(KurenaiGoではprotocol_version)を送ると解析はただちに中断され、 そのコマンド自身の正常な応答が届きます。この方式は繰り返しの実機検証で安定して動作したため、 KataGoClient::ExchangeAnalyzeでは停止に空行ではなくprotocol_versionを 使っています。

8.2 解析タイミングと打ち切り

解析は経過時間(目安600ms)または最有力手のvisits数(目安250)のいずれかに達し次第打ち切り、 どちらも満たさない場合でも1500msでハードキャップします。応答が来るまでの間も KataGoClientの非同期パターン(RequestAnalysis / TryGetAnalysisResultのポーリング)により描画ループは止まりません。解析は 対局進行に必須ではない補助情報のため、失敗してもKataGoAnalysisResult::Failedで 通知するのみで、genmove失敗時のようなダイアログ表示・対局中断は行いません。

9. 棋譜の保存・再生(SGF)

KurenaiGo::Sgf(Source/Sgf.h/.cpp)は、対局の記録をSGF (Smart Game Format)として書き出す・読み込む機能を提供します。分岐(variation)の無い 単一手順のみを扱う最小限のサブセットで、自分自身が書き出したSGFを読み戻せることを 目的としています。

9.1 座標変換

SGFの座標は列→行の順でa〜s(0〜18)、行は盤面上端が0です。KurenaiGoの内部座標 (row=0が盤面下端)との変換はsgfRow = (Size-1) - rowで、8.1節で 説明したkata-analyzeのownership配列と同じ変換則を再利用しています。パスは B[]/W[](空値)で表します。

9.2 保存の流れ

Main.cppは対局中、黒白どちらの着手・パスもstd::vector<SgfMove> (moveHistory)へ記録します。対局終了(自分の投了・KataGoの投了・ final_scoreによる終局のいずれか)の時点で、結果文字列 (自分の投了→"W+R"、KataGoの投了→"B+R"、終局→final_scoreの 応答をそのまま使用)とともにGames\フォルダ(実行ファイルと同じ場所、 ResolveAppDataPath(L"Games"))へ、タイムスタンプ付きファイル名 (game_YYYYMMDD_HHMMSS.sgf)で保存します。棋譜保存は対局結果の表示を妨げない 補助機能のため、失敗しても例外は投げずerror.logに記録するのみです。保存先パスは lastSavedGamePathとして保持し、9.3節の棋譜再生で読み直すのに使います。

9.3 棋譜再生(Reviewing)

TurnState::Reviewingという状態を追加し、対局終了(GameOver)後に Vキーを押すとlastSavedGamePathをReadSgfFileで読み直して 遷移します(メモリ上のmoveHistoryを使い回さず、実際にファイルから読み直すことで 読み込み機能そのものを検証しています)。再生中はreviewMoveIndex(現在何手目まで 進めたか)を持ち、→/←キーで[0, 総手数]の範囲を前後します。

GoBoardには手を戻す操作が無いため、reviewMoveIndexが変化するたびに 空のGoBoardを新しく作り、0手目からreviewMoveIndex手目の直前まで TryPlay/Passを再生し直して盤面を再構築します(ReplayMoves)。 19路・数百手程度の対局であれば、ナビゲーションのたびに毎回再生し直すコストは無視できるため、 差分更新は行っていません。この盤面再構築は表示専用で、9.4節のKataGo側の解析とは別経路です。

9.4 再生中の解析表示・損失グラフ

棋譜再生中に着手位置(reviewMoveIndex)を動かすと、その局面をKataGoにも解析させます。 対局中のkataGo(KataGoClient)は対局の最新局面を指したままのため、 KataGoClient::ResetBoard()(clear_boardを送るだけの同期呼び出し)で 盤面を空にしてから、0手目から対象の手数の直前までPlayMove/PlayPassで 再生し直し、その局面の手番(0手目なら黒、それ以外は直前の手のOpponent)で RequestAnalysisを要求します(Main.cppのrequestReviewAnalysisFor)。 呼び出し側のtriggerReviewAnalysisIfNeededは現在の手数を優先しつつ、手が空いていれば 9.5節の言語化に使う1手前の局面もあわせて解析します。

解析結果は手数ごとにreviewWinrateCache/reviewScoreLeadCache (黒視点に変換済み)へキャッシュし、一度解析した手数を再訪した場合は即座に表示します。 KataGoは1件ずつしかリクエストを処理できない設計のため、解析要求中 (reviewAnalysisPendingIndex != -1)は次のreset/replayを送らず、前の解析が 終わるまで待ちます。これにより素早く連続してナビゲーションしても描画ループがブロックされることは ありません(ただし、初めて訪れる手数は解析(通常600ms〜1.5秒)+再生コストの分だけ表示が 遅れます。数百手を再生し直す場合、再生自体も同期呼び出しのため体感できる遅延が出ることがあります が、リアルタイム対局とは異なる「棋譜再生」機能として許容範囲と判断しています)。

解析結果の表示(DrawWinrateText)は対局中・再生中どちらでも同じ値 (ToBlackWinrate/ToBlackScoreLead)を使い、勝率バーの下に 「黒 62.3% 目差 +4.5」のように数値で表示します。損失グラフ(DrawLossGraph)は 盤の上部に確保した帯(kGraphAreaHeight、対局中は空のまま)に、手数ごとの黒視点勝率を 折れ線で描画します。キャッシュ済みの区間のみ線分を結ぶため、未解析の手数は線が途切れ、 現在の手数には小さな丸印を表示します。全手数の一括先読みは行わず、訪れた手数だけ解析する 遅延評価方式のため、グラフは棋譜を辿るにつれて徐々に完成していきます。

9.5 着手の言語化

損失グラフの上には、その手数に至った1手(reviewRecord.Moves[reviewMoveIndex - 1])が どの程度の手だったかを日本語の文章で表示します(BuildMoveCommentary)。着手前後の 局面の評価が両方キャッシュ済みになった時点で、着手した側の視点に変換した勝率 (ToBlackWinrateの値を、着手者が白なら1 - 値にする)の差分から 分類します。

勝率の変化(着手者視点)表示
-2ポイント以上、または着手前の局面でKataGoの最有力候補手(Order == 0)と一致最善手級です
-2〜-5ポイントやや損な手です
-5〜-15ポイント緩着です
-15ポイント未満悪手です

最善手でなかった場合は、着手前の局面でのKataGoの最有力候補手の座標をFormatVertex (KataGoClient::ToVertexと同じA〜T(Iを除く)+行番号の表記)で文中に 添えます。この閾値はKataGoを使った解析ツールで一般的に用いられる目安を参考にした一例であり、 手筋の正しさを厳密に判定するものではありません(死活・シチョウ・ヨセ等の詳細な分類は今後の 課題とし、13章参照)。

言語化には着手前の局面の評価・最有力候補手も必要なため、 requestReviewAnalysisFor(target)という関数に一般化し、 triggerReviewAnalysisIfNeededは現在の手数を優先しつつ、要求が不要だった場合 (=現在の手数はすでに解析要求済みか解析済み)に限り1手前の局面もあわせて要求します。KataGoは 1件ずつしかリクエストを処理できないため、現在の手数の表示を遅らせてまで1手前を優先することは ありません。前後どちらかが未キャッシュの間は「解析中...」と表示します。最有力候補手の座標は reviewBestMoveRowCache/reviewBestMoveColCacheとして、勝率・目差の キャッシュ(9.4節)と同様に手数ごとにキャッシュします。

このコメント表示の分だけ、盤上部の帯の高さ(kGraphAreaHeight)を90pxから130pxへ 拡張し、損失グラフ(9.4節)はその下に詰めて描画するようレイアウトを調整しました。

9.6 新規対局(何度でも打ち直せる)

GameOver・Reviewingのどちらの状態からでも、新規対局 ボタン(Nキー)でMain.cppのstartNewGameを呼び、 アプリを再起動せずに何度でも対局をやり直せます。startNewGameはmoveHistoryを クリアしたうえでTurnState::ChoosingBoardSize(10.5節の盤の大きさ選択)へ戻します。 board(GoBoard)自体は盤の大きさボタン(9路/13路/ 19路)を選んだ時点で新しい大きさの空盤面として作り直されます。以降は初回起動時と 同じ経路(盤の大きさ選択→モード選択→(カジュアルのみ)強さ選択→KataGo起動)を通って黒番(人間)の 手番から再開します(11.1節参照。対局ごとに強さを変えるため、新規対局のたびにKataGoを起動し直す)。

lastSavedGamePath・直前のreviewRecordはあえてクリアしません。次の対局が 終わればFinalizeGameResultがlastSavedGamePathを新しい保存先で上書きし、 棋譜再生ボタンから改めて読み直す(9.3節)ため、古い値を保持しておいても実害が ないためです。

Reviewing中は解析要求中(9.4節)を避けてからResetBoard()を 呼ぶ: 9.4節の通りKataGoClient::ExchangeAnalyzeは解析中ずっと m_IoMutexを保持し続ける設計のため、解析要求中(reviewAnalysisPendingIndex != -1)にResetBoard()(内部で同期的にExchange("clear_board")を 呼ぶ)を呼ぶと、解析が終わるまで描画ループがブロックされてしまいます。これは requestReviewAnalysisForが解析要求中の再要求を避けているのと同じ理由のため、 Reviewing状態でのNキー/ボタンはreviewAnalysisPendingIndex == -1の間だけstartNewGameを実行し、解析要求中は1フレーム見送ります(次に押した ときには解析が終わっているのが通常のため、実用上は連打すればすぐに反応します)。 GameOver状態ではその時点で進行中のKataGoリクエストが無いため、この待ち合わせは 不要です。

10. 棋力の数値化(レーティング)

KurenaiGo::Rating(Source/Rating.h/.cpp)は、対局結果からユーザーの レーティング(棋力の数値化)を計算・永続化する。標準的なElo式を使い、対局相手(KataGo)の レーティングとの相対評価として計算する。11章の通り、レート戦ではAIの強さ自体をこの ユーザーレーティングに合わせて毎回調整するため、Elo式のopponentRatingには 固定値ではなく「その対局で目標とした強さ(レーティング換算)」を渡す。 

expected = 1 / (1 + 10^((opponentRating - userRating) / 400))
newUserRating = userRating + K * (actualScore - expected)

ユーザーの初期値はkInitialRating = 0(11.6節の段級位換算における30級=最弱到達点に 相当する値。11.3節のプレースメントモードの基準アンカー値としても使うが、同モードは現在 11.6節の理由により無効化している)、K係数はkEloK = 32(Eloで広く 使われる一般的な値)。 actualScoreは勝敗のみ(1.0=勝ち/0.0=負け/0.5=持碁)で、目差による重み付けは 行わない(標準Elo外の独自ルールになるため採用していない)。

実世界の段級位を表す値ではない: レート戦は常にAIの強さをユーザー自身の レーティングへ合わせにいく設計(11章)のため、Elo式の期待勝率は理論上常に0.5に近づき、 勝敗によるレーティング変動は概ね±K/2(≒16点)相当になる。このレーティングは 「その時点で自分と互角になるよう調整された相手に対する、勝ち越し・負け越しの推移」を 数値化したものであり、KataGoや自分自身の実力を客観的な段級位で評価したものではない。

10.1 対局モード(レート戦/カジュアル)

対局モードの選択は、当初MB_YESNOのShowMessageBoxUtf8によるモーダル ダイアログとして実装していたが、11章のカジュアル強さ選択(5段階)を追加するにあたり、 既存の盤下ボタン行(ButtonSpec/DrawButton)による選択に統一した (モーダルダイアログを使い続ける理由が無くなったため。TurnState::ChoosingBoardSize (10.5節、盤の大きさ選択)の直後のTurnState::ChoosingGameModeで 「レート戦」/「カジュアル」の2択を、カジュアルを選んだ場合のみ続けて TurnState::ChoosingCasualStrengthで強さの5段階を選ぶ)。選択結果は GameMode::Ranked/GameMode::Casualとして対局中保持され、盤下のHUDに 常時表示する。カジュアルを選んだ場合、SGFの保存(9章)は今まで通り行うが、レーティングの 更新・履歴への追記は一切行わない。

10.2 対局結果文字列からの勝敗判定

対局終了時の結果文字列("W+R"=人間の投了、"B+R"=KataGoの投了、 またはfinal_scoreの応答、例"B+3.5")から、 TryParseBlackWinFractionが黒番(人間)視点の勝敗を取り出す。 "B+"で始まれば勝ち(1.0)、"W+"で始まれば負け(0.0)、 "0"(持碁)は0.5とする。解釈できない文字列の場合はレーティングを更新せず error.logに記録するのみとする(存在しないデータを捏造しない)。

10.3 永続化(rating_history.txt)

現在値だけでなく対局を跨いだ推移を追えるよう、レート戦の結果が出るたびに1行 追記する履歴ファイルとして設計している(rating_history.txt、 ResolveAppDataPathでexeと同じフォルダに解決)。1行のフォーマットは <YYYYMMDD_HHMMSS> <この対局後のレーティング> <対局結果文字列> (BuildGameFileNameと同じput_time呼び出しを流用したタイムスタンプ)。 通常の対局結果文字列("W+R"等)に加えて、11.3節の初期レーティング決定 (プレースメント)で確定した行は結果欄が"PLACEMENT"になる(収束による確定・ 収束前に対局が終わったことによるフォールバック確定のいずれも同じ表記とし、通常の対局結果とは 異なる由来であることが履歴から分かるようにするため)。起動時は全行を読み、パースできた行数を 対局数、最後の行の値を現在のレーティングとして復元する(LoadRating、ファイル 不在・全行パース失敗時は初期値にフォールバックし例外は投げない)。今回のパスでは推移の記録の みを行い、グラフ等での可視化(9.4節の損失グラフに相当するもの)は未実装(13章参照)。

10.5 盤の大きさ(9路/13路/19路)ごとの分離

TurnState::ChoosingBoardSizeをChoosingGameModeより前に追加し、起動直後・ 新規対局(9.6節)のたびに最初に通る状態にした。盤下ボタン(9路/13路/ 19路)を選ぶとcurrentBoardSize(Main.cpp)にその値を保持し、 board(GoBoard)をその大きさで作り直してからChoosingGameMode (10.1節)へ進む。currentBoardSizeはComputeBoardLayout・ DrawBoard・KataGoClient::StartAsync(GTPのboardsizeコマンド)・ SGF書き出し(SgfGameRecord::BoardSize)など、盤の大きさに依存するすべての箇所に渡す (2〜3章参照)。

9路・13路・19路は互角になる強さの基準がまったく異なるため、レーティングは盤の大きさごとに 完全に独立したファイルで管理する(rating_history.txt=19路、 rating_history_13.txt=13路、rating_history_9.txt=9路。いずれも ResolveAppDataPathでexeと同じフォルダに解決)。19路は既存ユーザーの rating_history.txtをそのまま使い続けるため、ファイル名は変更していない。 Main.cppは起動時に3つともLoadRatingで読み込んでおき、 CurrentUserRating()/CurrentRatingPath()という2つのラムダが currentBoardSizeに応じて対応するRatingData/パスへの参照を返す (10.1〜10.4節・11章のレーティング更新・AIの強さ計算は、すべてこの2つの参照経由で行うよう 書き換えた)。対局中に盤の大きさが変わることは無い(選び直しはChoosingBoardSizeのみ) ため、フレームごとに参照先を解決し直しても矛盾は生じない。

10.6 盤の星(hoshi)の標準的な配置

9路・13路は4隅+天元の5箇所(19路のような辺の星は無い)、19路は4隅+辺+天元の9箇所という、 それぞれの盤の大きさで広く使われる標準的な配置をHoshiPointsForBoardSize (Main.cpp)にハードコードしている。19路の9箇所は0-indexedで3・9・15の 3×3の組み合わせとして機械的に生成できるが、9路・13路は辺の星が無い非対称なパターンのため、 座標を1つずつ列挙している。

11. 棋力に応じたAIの強さ設定

レート戦・カジュアルいずれの対局でも、ユーザーが指定した(あるいはレート戦なら自動計算した) 目標レーティングに応じてKataGoの探索の深さ(maxVisits)を調整し、対局開始時に その強さでKataGoを起動する。

11.1 対局開始前に強さを確定し、強さが決まってからKataGoを起動する

M5時点では「体感の起動待ち時間を減らす」ため、kataGo.StartAsync(...)を呼んだ 直後にモード確認ダイアログを表示し、KataGoの起動完了を待たずに済ませていた。しかし本機能では 強さ(maxVisits)を起動時のコマンドライン引数としてしか指定できない (11.4節参照)ため、強さが決まる前にKataGoを起動してしまうと意味が無い。そのため モード選択→(カジュアルのみ)強さ選択→KataGo起動の順に変更した (体感の起動待ち時間は増えるが、正しい強さで起動するための必須の順序である)。

TurnStateにChoosingGameMode(「レート戦」/「カジュアル」の2択、 盤下ボタン)・ChoosingCasualStrength(カジュアル選択時のみ、強さ5段階の選択、 盤下ボタン)を追加した。強さが確定するとbeginGameWithTargetRating(targetRating) (Main.cpp)がComputeMaxVisitsForRatingでmaxVisitsを求め、 kataGo.StartAsync(...)を呼んでTurnState::EngineStartingへ遷移する (以降は既存の起動待ちポーリングをそのまま使う)。startNewGame(9.6節、新規対局)は 盤面・着手履歴をリセットしてChoosingGameModeへ戻すだけの処理に簡略化され、 初回起動時のセットアップと新規対局時のセットアップが同じ経路を通るようになった(その後10.5節で ChoosingGameModeの前にChoosingBoardSizeを追加した際も、 startNewGameの戻り先をChoosingBoardSizeに変えるだけで済んだ)。

11.2 レーティング→強さ(maxVisits)の写像(Human SLモデル未配置時のフォールバック)

constexpr int kMinAiVisits = 20;    // 弱め
constexpr int kMaxAiVisits = 500;   // gtp.cfgの元の既定値をそのまま上限に使う
constexpr double kAiStrengthScalingMinRating = 1000.0; // これ以下はkMinAiVisits
constexpr double kAiStrengthScalingMaxRating = 2000.0; // これ以上はkMaxAiVisits

目標レーティングをこの範囲で線形補間してmaxVisitsを求める (ComputeMaxVisitsForRating、Main.cpp)。レート戦の目標レーティングは 常にCurrentUserRating().Rating(現在選択中の盤の大きさでの自分のレーティングと 互角の相手にする設計、10.5節参照)。

maxVisitsと実際の強さの対応は較正されていない目安: 探索visits数と 対局相手としての実際の強さの対応関係は、ハードウェア・局面の複雑さ・ネットワークに依存し 普遍的な換算式は存在しない。このため上記の範囲・写像は「妥当だと考えられる調整可能な目安」で あり、科学的に較正された対応表ではない(10章のレーティング自体が実世界の段級位を表さないのと 同じ立場)。この写像は現在、Human SLモデル(11.6節)が使えない場合(未配置時)専用の フォールバックとして使われている。通常はHuman SLモデルによる段級位ベースの強さ決定 (11.6節)が優先される。

11.3 初期レーティング決定(プレースメント)モード

現在いったん無効化中: 11.6節のレーティング基準点変更(1500→0)に伴い、 以下のEMA・収束判定まわりの初期値も合わせて再検討する必要があるため、Main.cppの constexpr bool kPlacementModeEnabled = false;で無効化している。無効化中は 対局回数0のユーザーも通常のレート戦としてレーティング0(30級相当)から即座に対局を始める (isCurrentGamePlacementが常にfalseになるだけで、以下の PlacementTracker本体・関連コードは再有効化に備えて削除せず残している)。

対局回数0(CurrentUserRating().GamesPlayed == 0、盤の大きさごとに別々に判定、 10.5節参照)のままレート戦を始めた場合のみ発動する(有効化されていれば)。強さの決め方自体は 11.2節と同じ。特別なのは、対局中にレーティング 推定値を追跡し、収束したら対局の結果を待たずにその時点で確定する点である。

黒(人間)の手番になるたびにすでにkata-analyzeで取得している WinrateForColorToMove(黒視点勝率、8章)を、Eloの期待勝率式の逆算に使う。 

// expected = 1/(1+10^((opponentRating-rating)/400)) をratingについて解いた式
double InvertEloForRating(double expectedScore, double opponentRating);

Rating.h/.cppにComputeEloDeltaと対になる関数として追加した。 Main.cppのPlacementTracker構造体が、手番ごとの勝率を指数移動平均 (EMA、重み0.15)へ取り込み、InvertEloForRatingで瞬間推定レーティングを求めて 直近8件の履歴を保持する。この直近8件から「収束率」(PlacementTracker::ConvergenceRate()、 0.0〜1.0)を計算し、kConvergenceRateThreshold(0.8=80%)以上になった時点で 「収束」とみなす。収束率は、サンプル数がまだ少ない間(kMinSamples=10未満、または 直近ウィンドウが8件埋まっていない間)は幅(spread)を評価するだけのデータが揃っていないため、 サンプル数の到達度(kMaxSamples=60に対する割合)のみを使う。データが揃った後は、 「直近8件の幅(spread)がkConvergenceThreshold(15点)未満に近づいた度合い」と「サンプル数が kMaxSamplesに近づいた度合い」のうち大きい方を採用する(どちらか一方の基準を満たせば収束と みなすため)。収束したら、直近8件の平均値を確定レーティングとして現在選択中の盤の大きさに 対応する履歴ファイル(CurrentRatingPath()、10.5節)へ結果"PLACEMENT"で 追記した上で、対局自体もその場で終了する(GamesPlayedが0から1に なり、以降は通常のレート戦になる。SGFの結果欄には"Void"を記録し、投了・終局後解析 (11.5節)は他の終局経路と同様に走らせる)。収束(80%)に達する前に投了・終局してしまった場合は この対局ではレーティングを確定させない(finalizePlacementRating()ラムダを呼ばない) ため、GamesPlayedは0のままとなり、次のレート戦もプレースメントとして再開される (複数局にまたがって収束させる想定どおりの挙動)。この「再開」の際、PlacementTracker 自身(Active・EMA・サンプル)は前の対局の状態のまま次の対局へ引き継がれる (beginGameWithTargetRatingが、直前の盤の大きさBoardSizeと今回の currentBoardSizeが一致し、かつまだActiveな場合のみ Reset()を呼ばないようにしている)。盤の大きさを変えた場合や、間にカジュアル対局を 挟んだ場合はReset()され、収束率は0%から再スタートする(レーティングが盤の大きさ ごとに別々に記録される10.5節の設計と整合させるため)。 HUDには通常のレーティング表示の代わりに「レーティング測定中(推定: … 収束率: …%)」を表示する (収束率は上記ConvergenceRate()を百分率にしたもので、厳密な確率的意味を持つ値では なく、プレースメント中の体感的な目安として表示するものである)。

実装中に発見・修正したバグ: 同じ解析結果を複数回サンプリングしてしまう: KataGoClient::TryGetAnalysisResultは一度取得した解析結果を、次の RequestAnalysisが呼ばれて上書きされるまで、呼び出すたびにtrueを 返し続ける設計になっている(8章の勝率バー表示等ではこれで問題ない。同じ値を毎フレーム 再描画するだけのため)。しかしPlacementTrackerへの統計的なサンプリングでは、 これにより「1手」のはずが1フレームごとに何度もサンプルとして取り込まれてしまい、実機検証で 1手しか指していないのにサンプル数が10に達し即座に(誤って)収束する不具合が発覚した。 enterHumanToMove()でfalseに戻すplacementSampledForCurrentTurn フラグを追加し、1手番につき1回だけサンプリングするよう修正した。

実装中に発見・修正したバグ: 収束しても対局が最後まで打ち切られてしまう: 当初の実装は「収束したらその場でレーティングを確定する」処理は持っていたが、確定後も対局自体は 最後まで打ち切る設計になっており、「ある程度収束したら対局自体を終了する」という要求と 合っていなかった。収束を検知した時点(この時点でturnStateは必ずHumanToMove。 RequestAnalysis(Stone::Black)はenterHumanToMove()でのみ呼んでいるため)で 即座に終局処理(SGF保存・対局後解析・GameOverへの遷移)まで行うよう修正した (finalizePlacementRating()ラムダに確定処理を切り出し、収束を検知した箇所から呼ぶ)。 なお、収束(80%)に達する前に投了・終局してしまった場合にレーティングを確定させず GamesPlayedを0のまま次のレート戦もプレースメントとして再開させるのは、 9路・13路など手数の少ない対局で信頼できるサンプルが集まる前に決着してしまうケースを想定した 意図的な仕様であり(「収束するまで複数局かかることがある」)、バグではない。

実装中に発見・修正したバグ: 対局開始直後の数手で収束率が異常に高く出る: ConvergenceRate()の当初の実装は、サンプル数が少なくても直近ウィンドウの 最大-最小(spread)を無条件に計算していた。サンプルが1〜数件しか無い段階ではこの幅が 偶然小さくなりやすく(極端な場合はサンプル1件でspreadが0になる)、結果として対局開始 直後の数手だけで収束率が100%近くまで跳ね上がって表示される不具合があった。 SampleCount < kMinSamplesまたは直近ウィンドウがkConvergenceWindowSize (8件)埋まっていない間はspreadによる計算を行わず、サンプル数の到達度 (kMaxSamples=60に対する割合)のみを収束率として返すよう修正した。この間は 分母が60と大きいため、収束率が序盤だけで跳ね上がることはない。

実装中に発見・修正したバグ: 2局目になると収束率がリセットされてしまう: 収束(80%)に達する前に対局が終わり、次のレート戦もプレースメントとして再開される場合でも、 当初の実装はbeginGameWithTargetRatingで毎回無条件にplacementTracker.Reset() を呼んでいたため、前の対局で積み上げたEMA・サンプルが対局のたびに失われ、収束率が毎回0%から やり直しになってしまっていた(実機検証で発覚)。PlacementTrackerに現在追跡中の 盤の大きさを保持するBoardSizeフィールドを追加し、「今回もプレースメント対象」かつ 「まだActive」かつ「盤の大きさが前回と同じ」の3条件がすべて揃う場合のみ Reset()を呼ばずに前の対局の状態を引き継ぐよう修正した。盤の大きさを変えた場合は 別のレーティング(10.5節)を測定することになるため、意図的にリセットする。

11.4 実機検証: -override-config maxVisitsの効果

gtp.cfgのコメントに「全パラメータは-override-config KEY=VALUE,KEY=VALUE,...でコマンドライン上書きできる」と明記されているが、実際に genmoveの探索に効くかどうかは実機で検証した。time_settings 0 5 1 (本アプリの実運用と同じbyoyomi 5秒)のもとでgenmoveの応答時間を比較したところ、 maxVisits=20で約0.15秒、既定のmaxVisits=500で約0.79秒、 極端に大きいmaxVisits=100000で約3.0秒(5秒のbyoyomiに近づく)となり、 maxVisitsが小さいほど探索が早く打ち切られることを確認した。一方、 kata-analyze(解析表示用、8章)はmaxVisits=20を指定しても 数百visitsまで報告が伸び続けることも確認しており、kata-analyzeの解析量は maxVisitsに縛られない場合がある(表示用の解析量と実際の着手決定の探索量は 別物である点に注意)。

11.5 KataGoClient: 同一インスタンスでの再起動

対局ごとに強さを変えるため、対局開始のたびにStartAsyncを呼び直す(9.6節の startNewGameも含む)。デストラクタの本体(ワーカースレッドjoin後の後始末: quit送信→プロセス終了待ち→ハンドルクローズ)をShutdownProcessIfRunning() として切り出し、StartAsyncの冒頭でも(既存プロセスがあれば)呼ぶことで、 同一KataGoClientインスタンスを安全に「作り直せる」ようにした。あわせて m_StartupComplete等のアトミックフラグもここでリセットし、前回セッションの 状態が残らないようにしている。

11.6 Human SLモデルによるアマチュア向けの強さ再現

11.2節のmaxVisits線形補間は、探索回数を絞ってもKataGoの政策ネット自体の 一手の質が高いままのため、初心者〜アマチュアが対局しても「弱いAI」だと体感しにくいという 限界がある。KataGo公式はこの課題に対して「Human SLモデル」 (-human-model起動引数、humanSLProfile設定)を提供している。 これは政策ネットの代わりに人間の棋譜から学習したモデルを使い、rank_20k〜 rank_9dのように実際の級位・段位を指定して、その棋力の人間の打ち筋(悪手も含む)を 再現するもの(同梱のgtp_human5k_example.cfg参照)。導入済みのKataGo実行ファイルは v1.16.5(-human-modelが入ったv1.15.0以降)であることを 実機ログ(katago_stderr.log)で確認済み。盤の大きさ(9路/13路/19路)を問わず、 Human SLモデルファイルが配置されていれば常にこちらを優先して使う。

11.6.1 レーティング↔段級位インデックスの変換

レーティングの範囲を0〜上限なしとし、段級位は30級(最弱、index 0)〜段位は上限なし (1段=index 30、9段=index 38、10段以降も理論上続く)として、レーティングが段級位インデックスの 3乗に比例するようにする(Main.cppのRankIndexForRating/ RatingForRankIndex)。基準点として1段のレーティングをちょうど1000にすることで、 rating = index3 / 27、逆にindex = 3 * cbrt(rating)という 単純な式になる。 

constexpr int kRankIndexForOneDan = 30; // 30級(index0)〜1級(index29)の30段階の直後が1段
constexpr double kRatingForOneDan = 1000.0;

double RankIndexForRating(double rating) { return kRankIndexForOneDan * std::cbrt(std::max(0.0, rating) / kRatingForOneDan); }
double RatingForRankIndex(double rankIndex) { return (rankIndex * rankIndex * rankIndex) / 27.0; }

段位が上がるほど1段の重みが増す換算は較正されていない目安: 11.2節のmaxVisits 写像と同じ立場で、実世界の段級位を保証する対応表ではなく、調整可能な目安である。

KataGoのhumanSLProfileが実際にサポートするのは20級〜9段のみ(同梱 gtp_human5k_example.cfgのコメント記載の範囲、"RANK from 20k to 9d")のため、 HumanSLProfileSuffixForRankIndexはこの範囲(index 10〜38)にクランプしてから "20k"〜"9d"形式の文字列を作る。表示用の段級位 (DisplayRankTextForRankIndex、HUDの「AI強さ(目安)」に併記)はクランプせず 理論値をそのまま見せる。

初期レーティング(0)との組み合わせによる注意点: kInitialRating (Rating.h)を1500から0へ変更したのは、この段級位換算で0が30級(最弱到達点)に ちょうど対応するようにするため。11.3節のプレースメントモードを無効化しているのも同じ理由 (基準点変更に伴う再設計が必要なため)。

11.6.2 カジュアル対局の強さ選択UI(盤上のタブ+5列2行グリッド)

従来の「自分のレーティングからの相対オフセット5段階」(とても弱め/弱め/おすすめ/強め/ とても強め)は、20級〜9段(段級位インデックス10〜38、ちょうどKataGo対応範囲と一致)から 直接選べるUIに置き換えた。盤の中央に3つの範囲タブ(「20〜11級」「10〜1級」「1〜9段」、それぞれ 段級位インデックス[10,19]/[20,29]/[30,38]に対応)を表示し、選択中のタブの範囲を5列2行の ボタングリッドで表示する(20〜11級・10〜1級はちょうど10個で埋まり、1〜9段は9個のため 最後の1マスは空ける)。ChoosingCasualStrengthに入った時点で、現在のユーザー レーティングが属する範囲のタブを既定選択にする。右側縦列のボタン(LayoutButtonColumn) とは別に、盤中央基準の専用レイアウト関数(LayoutCasualGroupTabs/ LayoutCasualRankGrid)を追加したが、ButtonSpec/ButtonRect/ DrawButton/IsPointInButtonは右側縦列と共通のものをそのまま再利用している。

StartAsync/LaunchProcessにhumanModelPath・ humanSLProfileを追加した。humanSLProfileが非空の場合のみ -human-model "<humanModelPath>"をコマンドラインに追加し、 -override-configにhumanSLProfile・ humanSLChosenMoveProp=1.0・humanSLChosenMoveIgnorePass=true・ humanSLChosenMovePiklLambda=100000000・useLcbForSelection=false・ rootNumSymmetriesToSample=2・chosenMoveTemperature*系(いずれも同梱 gtp_human5k_example.cfgの値を踏襲)をmaxVisits=40とあわせてカンマ区切りで 付与する。空文字列の場合(Human SLモデル未配置時)はmaxVisits=<レーティングから計算した値> のみを付与する従来方式に完全にフォールバックする。

実機検証: Human SLモデル本体(b18c384nbt-humanv0.bin.gz、約90MB超)は 容量が大きいため開発機に常設していないが、検証のためダミーファイル(ランダムバイト列)を 同じファイル名で配置してカジュアル対局を開始したところ、katago_stderr.logに Uncaught exception: Error loading or parsing model file ...\KataGo\b18c384nbt-humanv0.bin.gz: Error while ungzipping file, Z_DATA_ERROR. Invalid file? という、指定したパスのファイルを実際に読み込もうとした形跡のあるエラーが記録されることを確認した (-human-model・-override-configのコマンドライン構文自体はKataGoに 正しく解釈されている証拠になる)。この際KataGoプロセスは起動直後に終了するため、 KataGoClient::Exchangeの応答読み取りが失敗し、アプリ側は error.logに「KataGoの起動に失敗しました」と記録したうえでクラッシュせず 処理を継続することも確認した(9章の起動失敗時のエラーハンドリングがそのまま機能している)。 実際の学習済みHuman SLモデルでの人間らしい打ち筋そのものの検証は、本体ファイルを配置した うえで別途行う必要がある。

実機検証: Human SLモデル未配置時のフォールバック経路(19路・カジュアル・ 「1〜9段」タブの「1段」ボタン)で対局を開始し、KataGoが通常モデル(model.bin.gz) のみで正常に起動し、HUDに「AI強さ(目安):1000 [1段相当]」と表示されること、黒番(人間)の 手番・kata-analyzeによる勝率バー表示が従来どおり機能することを確認した。 また、この過程で当初の実装に2件の不具合を発見し修正した: (1) RatingData::Ratingの デフォルト値がkInitialRatingと独立に1500.0のままハードコードされて おり、新規ユーザーが常に1500からスタートしてしまっていた(Rating.hで double Rating = kInitialRating;に修正)。(2) ChoosingCasualStrengthの 右側縦列ボタン組み立てでelse if分岐を丸ごと空にした際に条件式ごと削除してしまい、 どの条件にも一致せず最後のelse(通常対局中のボタン)へフォールスルーしていたため、 強さ選択画面に「地合い表示」「着手ヒント」ボタンが誤って表示されていた(明示的な空の else if (turnState == TurnState::ChoosingCasualStrength) { }分岐を追加して修正)。

12. 苦手分野の解析

局面(序盤/中盤/終盤)ごとの悪手率を、レート戦の対局が終了するたびに自動的に集計する。 KataGoから得られる勝率という事実ベースの情報だけで判定できる範囲に留め、「攻め/受け」 「死活」等の意味づけ(9.5節の言語化の延長として要望はあるが優先度最低で保留中、13章参照) には踏み込まない。

12.1 局面の3分割(序盤/中盤/終盤)

科学的な布石理論に基づく境界を判定する手段が無いため、単純にその対局の総手数に 対する割合で3等分する(MistakeStats.h/.cppのDeterminePhase、 1/3以下が序盤、2/3以下が中盤、それ以外が終盤)。この閾値は妥当だと考えられる単純な目安で あり、囲碁理論上の厳密な布石・中盤・ヨセの境界ではない。

12.2 分類ロジックの共通化

9.5節の着手の言語化にインライン化されていた4段階判定(最善手級/やや損な手/緩着/悪手)を ClassifyMoveQuality(deltaPercent, isBestMove)として切り出し、 BuildMoveCommentaryと本機能の両方から呼ぶ(判定基準を2箇所に重複させない)。

12.3 集計のタイミング: レート戦終了時の自動解析

棋譜再生(9.3節)への集計フックではなく、レート戦の対局が終了した時点で、 その対局の全手を自動的に解析して集計する(カジュアル対局は対象外)。 FinalizeGameResult呼び出し直後、レート戦の場合のみ beginPostGameAnalysisが終了した対局のmoveHistoryのコピーを保持して 状態を初期化し、以後は毎フレームadvancePostGameAnalysisIfNeededが requestReviewAnalysisFor(9.4節)と同じ手順(ResetBoard→0手目から 再生し直す→RequestAnalysis)で1手ずつ解析要求を送る。着手前後の勝率が両方 揃った時点でその着手を分類し、mistake_stats.txtへの重複排除キー ("<SGFファイル名>:<手数>")がまだ無ければ集計へ加算する。

12.4 解析完了までのブロック

1手あたり数百ms〜数秒かかり、数百手の対局では完了まで数分かかり得る。ユーザーの選択により、 解析が完了するまで「新規対局」「棋譜再生」ボタン・N/Vキーを 無効化する(ButtonSpec.Enabledと各キー判定の両方で postGameAnalysisActiveをガードする)。これにより、自動解析中に他の経路 (新しい対局のライブ解析、棋譜再生の解析)がKataGoの解析チャンネルを同時に使うことが 無くなるため、複数の要求元が競合する問題を考えずに済む(この自動解析だけが唯一の 解析要求元になる)。HUDには「対局後の解析中 (42/183手)」のように進捗を表示する。

KataGo通信の失敗は解析を打ち切るのみで対局・アプリ全体を止めない: 自動解析は補助機能であり、かつ完了までナビゲーションをブロックする設計のため、途中で KataGoとの通信が(何らかの理由で)失敗した場合にそのまま止まってしまうとブロックが解除 されなくなる。そのためadvancePostGameAnalysisIfNeededのKataGo呼び出し全体を try/catchで囲み、例外時はerror.logに記録したうえで postGameAnalysisActiveをfalseに戻し、ブロックを解除する。

12.5 永続化(mistake_stats.txt)

rating_history.txtと同じ「追記型ログ+読み込み時に集計・重複排除」のパターンを 踏襲する。1行のフォーマットは <SGFファイル名> <手数> <phase> <quality> (例: game_20260725_201055.sgf 42 Middle Loose)。起動時に LoadMistakeStatsが全行を読み、局面×分類ごとの手数と、集計済みキーの集合 (SeenKeys)の両方を1回のスキャンで復元する(ファイル不在・パース失敗行は 無視し例外を投げない)。

12.6 表示: 「苦手分野」ボタン

TurnState::ViewingMistakeStatsを追加し、GameOver/Reviewing のボタン行に「苦手分野」ボタンを追加する(解析中でも閲覧できる。KataGoの解析チャンネルを 使わない純粋な読み取り表示のため、12.4節のブロックの対象外)。押すと盤の代わりに、 局面ごとの4段階の内訳・合計手数(BuildMistakeStatsLines)を表示し、 もっとも「緩着+悪手」の割合が高い局面を明示する。合計手数が10未満の局面には 「データが少なめです」と注記し、少ないサンプル数からの過信を避ける。「戻る」ボタンで 元の状態(GameOverまたはReviewing)に戻る。
