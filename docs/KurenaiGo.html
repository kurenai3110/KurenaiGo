KurenaiGo ドキュメント

KurenaiGoは、KurenaiEngine (KurenaiEngine2D)で描画し、KataGo をGTP経由の対局相手として使う囲碁(Go)アプリです。このドキュメントでは、アプリ本体 (KurenaiGo/Source/以下)の実装内容を説明します。KurenaiEngine自体のAPIリファレンスは KurenaiEngine/docs/KurenaiEngine.html を参照してください。

1. 現在の実装範囲KataGoとの対局・解析表示が可能

19路盤の表示、マウスでの着手、合法手判定・捕獲・シンプルコウを含むルール、そして KataGoをGTP(Go Text Protocol)経由の 子プロセスとして起動しての対局(人間=黒、KataGo=白)までを実装しています。あわせて、 kata-analyzeによる局面解析を使った勝率表示・地合い可視化・着手ヒント(8章)、 棋譜(SGF)の自動保存・再生・再生中の解析表示と損失グラフ(9章)も実装済みです。色の選択・ ハンディキャップ・対局のリスタートは未実装です(10章参照)。

2. 座標系とレイアウト

KurenaiEngine2Dのワールド座標はウィンドウのピクセル座標そのもので、原点は画面左下、 Y-upです(DrawSpriteのx, yはスプライト中心)。KurenaiGoではウィンドウの リサイズに追従できるよう、毎フレーム renderer.GetWidth()/GetHeight() から 盤のレイアウトを再計算しています(ComputeBoardLayout)。 

struct BoardLayout
{
    float CenterX;      // 盤の中心(ウィンドウ中心)
    float CenterY;
    float BoardExtent;  // 木目の盤面の一辺の長さ
    float GridExtent;   // 格子線が占める範囲の一辺の長さ(盤面より内側)
    float LineSpacing;  // 目の間隔 = GridExtent / (kBoardLines - 1)
};
  • BoardExtentはウィンドウの短辺 × kBoardExtentRatio(0.88)。 常に正方形になるよう短辺基準で計算する。
  • GridExtentはBoardExtent × kGridExtentRatio(0.90)。 盤面の外周に木目の縁が見えるよう、格子線の範囲を一回り小さくしている。
  • 格子線のインデックス(0〜18)からワールド座標への変換は GridIndexToCoordinateが行う(中心からGridExtentの半分だけ引いた位置を 起点に、LineSpacing刻みで並べる)。

3. 盤・石の描画

盤面(木目)はCreateSolidColorTexture(255, 255, 255, 255)で作成した白1色のテクスチャを 木目色でティントした矩形スプライトで描画します。格子線・星・石はいずれも KurenaiEngine2D::DrawLine/DrawCircleで直接描画しており、円形テクスチャを 事前生成する必要はありません(かつてはTools/generate_stone_textures.ps1で石の PNGを生成していましたが、DrawCircleの追加に伴い削除しました)。

要素描画方法
盤面(木目)1x1の白テクスチャを木目色でティントした正方形スプライト1枚
格子線(縦横19本ずつ、計38本)DrawLineで格子の端から端まで1本ずつ描画
星(hoshi、3x3=9箇所)格子の交点(0-indexedで3, 9, 15)にDrawCircleで小さな点を描画
石(黒・白)GoBoardの石がある交点にDrawCircleで塗り円を描画

人間の手番中、カーソルに最も近い空点交点にはDrawCircleで半透明のプレビュー円を 表示します。

3.1 効果音

着手時(人間・KataGo双方)にstone_place.wav、対局終了(投了・両者パス後の final_score)にgame_end.wavをKurenaiEngineBase::PlaySoundで再生します。 いずれも実際の録音ではなく、Tools/generate_sound_effects.ps1で正弦波を合成して 生成した16bit PCMのWAVファイルです(Assets/Sounds/にコミット)。

4. ルールエンジン(GoBoard)

KurenaiGo::GoBoard(Source/GoBoard.h/.cpp)は盤面と囲碁のルールのみを 扱う、描画・入力から独立したクラスです。座標はrow=0が盤の下端・col=0が 左端(row*Size+colの1次元配列)で、これは2章のワールド座標系(インデックス0が下/左) およびGTPの座標系(行1=下端、列A=左端)の両方と一致するため、変換が単純になります。

4.1 合法手判定と捕獲

TryPlay(row, col, color)は次の順序で処理します。

  1. 空点でなければ非合法。シンプルコウで禁止されている地点なら非合法。
  2. 石を仮に置き、隣接する相手グループをフラッドフィル(CollectGroup)で走査して 呼吸点(liberty)を数える。呼吸点0のグループがあれば取り上げる(複数方向から同じグループに 到達する場合の重複除去あり)。
  3. 相手を取り上げた後、自分のグループの呼吸点を再計算する。0なら自殺手として非合法・ 全ての変更をロールバックする。
  4. 合法なら確定し、連続パス数を0にリセットする。取り上げた石の数はその色のアゲハマ (CapturesBy)に加算する(自殺手としてロールバックする場合は加算しない)。

4.2 シンプルコウ

直前の手が「相手をちょうど1つ取り、打った石自身が呼吸点1つ(その取った地点)だけの単独石になる」 形だった場合、その地点への即座の再着手を次の1手だけ禁止します(m_KoForbiddenIndex)。 パスを含むいずれかの着手が行われるとこの制約は解除されます。より厳密な超劫(局面の反復)判定は 行っておらず、一般的なアプリで広く使われる簡易版のコウ規則です。

4.3 地の計算をしない理由

GoBoard自体は地の計算(スコアリング)を行いません。生きた石・死んだ石の判定 (セキ等の特殊な形を含む)を自前実装するのは複雑で誤りやすいため、対局終了(両者パス)時は KataGoのfinal_score(7章)にスコアリングを委譲しています。

5. マウス・キーボード入力

KurenaiEngineBaseが公開するウィンドウスコープの入力API(IsMouseOverWindow・ WasMouseButtonPressed・WasKeyPressed・GetClientMousePosition)を 使っています。これらはウィンドウメッセージ(WM_MOUSEMOVE/WM_LBUTTONDOWN/ WM_KEYDOWN等)から状態を更新するため、GetAsyncKeyState/GetCursorPosと 異なりウィンドウがフォーカスを失っていれば反応しません。かつて必要だった、自ウィンドウのHWNDを FindWindowW(L"KurenaiEngineWindowClass", ...)で検索する回避策も、GetWindowHandleを 含むこれらのAPIが揃ったことで不要になりました。

GetClientMousePosition()はWin32標準のクライアント座標(原点は左上、Y-down)を返すため、 height - clientYでワールド座標(原点は左下、Y-up)に変換します。最も近い交点との距離が LineSpacingの40%以内であればその交点を「ホバー中」とみなします (TryGetHoveredIntersection)。クリック・パス・投了・地合い表示切替(T)・ 着手ヒント表示切替(H)はWasMouseButtonPressed/WasKeyPressedが すでに「直前のPumpEvents()呼び出し中に押された」立ち上がりエッジを返すため、 KurenaiGo側で前フレームとの比較を自前実装する必要はありません。

自動検証時の注意: IsMouseOverWindowは内部でTrackMouseEvent (TME_LEAVE)を使っており、これは実際のカーソル位置も見ています。PostMessageで WM_MOUSEMOVEを送ってウィンドウ内へカーソルがあるように見せかけても、実カーソルが ウィンドウ外にあると直後にWM_MOUSELEAVEが発生しIsMouseOverWindowが falseに戻ってしまう(ホバー判定だけが効かなくなる)ことを実機検証で確認しました。ホバー判定を 含めてPostMessageで動作確認したい場合は、実カーソルも対象ウィンドウのクライアント領域内に 置いた状態で行う必要があります。ボタン押下・キー入力自体(WasMouseButtonPressed/ WasKeyPressed)はこの制約を受けず、実カーソル位置に関係なくPostMessage/ SendMessageだけで正しく検証できます。

6. 対局の進行(状態遷移)

Main.cppのTurnStateで対局の進行を管理します。

状態内容
EngineStartingKataGo起動中。KataGoClient::IsStartupComplete()をポーリング
HumanToMove黒(人間)の手番。クリック/P/Rを受け付ける
AIThinking白(KataGo)のgenmove応答待ち。TryGetGenMoveResultをポーリング
WaitingForScore両者パス後、final_score応答待ち
GameOver対局終了。Vキーで棋譜再生(Reviewing)へ移れる(9.3節参照)
Reviewing棋譜再生中。→/←キーで手を進め戻しする

現在のTurnStateとアゲハマ数(GoBoard::CapturesBy)は、盤の下マージンに DrawTextで常時表示します(DrawHud、BuildStatusText)。 DrawTextはかな漢字を含むUnicode文字に対応しているため、表示文言は日本語です。 対局終了・投了・通信エラーのような割り込みが必要な通知は、既存のエラーダイアログのまま 残しています(進行中の状態はHUD、区切りとなるイベントはダイアログという役割分担)。

文字化けの修正: 本プロジェクトは/utf-8オプションでコンパイルしており、 ナロー文字列リテラル("...")はUTF-8でエンコードされる。これをMessageBoxAに そのまま渡すと、ANSI版はシステムのコードページ(日本語環境では多くの場合Shift-JIS)で解釈するため 日本語部分が文字化けする。Main.cppのShowMessageBoxUtf8で MultiByteToWideChar(CP_UTF8, ...)によりUTF-16へ変換してからMessageBoxWへ 渡すことでこれを解消している。KataGoClientの例外メッセージ(LastError())や std::exception::what()も同様にUTF-8として扱われるため、すべての通知はこのヘルパー 経由で表示している。

7. KataGo連携(KataGoClient)

KurenaiGo::KataGoClient(Source/KataGoClient.h/.cpp)は katago.exeをgtp -model <model.bin.gz> -config <gtp.cfg>で 子プロセス起動し、標準入出力を匿名パイプでリダイレクトしてGTPのテキストコマンド/応答を やり取りします(CreateProcessW + CreatePipeによるWin32の標準的な 「リダイレクトされた入出力を持つ子プロセス」の実装)。標準エラー出力(チューニング進捗等の 診断ログ)はKataGo/katago_stderr.logへリダイレクトしています。

7.1 非同期処理

起動処理(StartAsync)とKataGoの着手要求(RequestGenMove)・終局判定 (RequestFinalScore)は、OpenCLの初回チューニング(数十秒)やKataGoの思考時間 (time_settings 0 5 1で最大5秒/手)がかかるため、いずれも専用スレッドで実行します。 メインの描画ループはTryGetGenMoveResult等のポーリングで結果を受け取るだけなので、 KataGoが応答を返すまでの間もウィンドウは応答なしにならず、盤面の再描画・リサイズ処理を続けられます。

7.2 座標変換

GTPの座標は列がA〜T(Iを除く)、行が盤の下端から1始まりの数字です。 GoBoardの座標系(row=0が下端、col=0が左端)と対応しているため、 ToVertex/ParseVertexでの変換は「列インデックスに応じてAから 数え上げ、Iをまたぐ場合は1つ増やす」「行はインデックス+1」という単純な計算のみで 行っています。

7.3 GTPコマンド

コマンド用途
boardsize 19 / clear_board / komi 7.5 / time_settings 0 5 1起動直後のハンドシェイク(StartAsync)
play <B|W> <vertex|pass>人間の着手・パスをKataGo側の盤面にも反映する
genmove <B|W>KataGoに着手を生成させる。応答は着手・pass・resignのいずれか
final_score両者パス後の結果(例: B+3.5)取得
quit終了時にデストラクタから送信

7.4 終了処理

KataGoClientのデストラクタは、進行中のワーカースレッドの完了を待ってから quitを送信し、プロセス終了を最大3秒待って、それでも終了しない場合は TerminateProcessで強制終了します。これによりKurenaiGoを閉じてもkatago.exeが 残留しません。

8. 解析結果の可視化(勝率・地合い・着手ヒント)

黒(人間)の手番になるたびにKataGoClient::RequestAnalysis(Stone::Black)で kata-analyzeによる局面解析を要求し、結果をDrawWinrateBar (勝率バー)・DrawTerritoryOverlay(地合い可視化、Tキーでトグル)・ DrawMoveHints(着手ヒント、Hキーでトグル)の3つの描画関数で 可視化しています。KurenaiEngine2Dには文字描画機能が無いため、勝率は数値では なく黒/白の面積比を表す横棒、地合いは色つきの半透明オーバーレイ、ヒントは順位別に色分けした マーカーとして、すべて既存のDrawSprite(矩形スプライト)のみで表現しており、 この機能のためにエンジン(KurenaiEngineサブモジュール)側の変更は行っていません。

8.1 kata-analyzeのプロトコル(実機で検証)

kata-analyze <B|W> interval 50 ownership trueを送ると、GTPの即時応答 (= )は返らず、代わりにinfo move <頂点> visits N ... winrate W ... scoreLead S ... order K ... pv ... [次のinfo move...] ownership <361個の浮動小数> という1行の報告が定期的に再送され続けます(差分ではなく毎回全体を送り直す)。 winrate/scoreLead/ownershipはいずれも コマンド引数で指定した色(手番側)から見た値で、order 0の 候補手が最有力手(=現局面の評価値として使う値)です。ownership配列(19路なら 361要素)は盤面左上(GTPのA19)がindex 0で、右→下へ行優先(row-major)に 並びます。KurenaiGoの内部座標(row=0が盤面下端・col=0が左端)に 対応させると ownershipIndex = (Size - 1 - row) * Size + col となります (黒石をA19に置いて解析し、index 0付近の値が最も強く反応することを確認して検証済み)。

解析の停止方法に関する既知の癖: kata-analyzeは一般的には空行を送ると 停止しますが、このKataGoビルドでは「報告を受け取ってから短時間で空行による停止要求を送ると、 その後の応答が返らなくなる(ハングする)」現象を実機で複数回確認しました。空行の代わりに 通常のGTPコマンド(KurenaiGoではprotocol_version)を送ると解析はただちに中断され、 そのコマンド自身の正常な応答が届きます。この方式は繰り返しの実機検証で安定して動作したため、 KataGoClient::ExchangeAnalyzeでは停止に空行ではなくprotocol_versionを 使っています。

8.2 解析タイミングと打ち切り

解析は経過時間(目安600ms)または最有力手のvisits数(目安250)のいずれかに達し次第打ち切り、 どちらも満たさない場合でも1500msでハードキャップします。応答が来るまでの間も KataGoClientの非同期パターン(RequestAnalysis / TryGetAnalysisResultのポーリング)により描画ループは止まりません。解析は 対局進行に必須ではない補助情報のため、失敗してもKataGoAnalysisResult::Failedで 通知するのみで、genmove失敗時のようなダイアログ表示・対局中断は行いません。

9. 棋譜の保存・再生(SGF)

KurenaiGo::Sgf(Source/Sgf.h/.cpp)は、対局の記録をSGF (Smart Game Format)として書き出す・読み込む機能を提供します。分岐(variation)の無い 単一手順のみを扱う最小限のサブセットで、自分自身が書き出したSGFを読み戻せることを 目的としています。

9.1 座標変換

SGFの座標は列→行の順でa〜s(0〜18)、行は盤面上端が0です。KurenaiGoの内部座標 (row=0が盤面下端)との変換はsgfRow = (Size-1) - rowで、8.1節で 説明したkata-analyzeのownership配列と同じ変換則を再利用しています。パスは B[]/W[](空値)で表します。

9.2 保存の流れ

Main.cppは対局中、黒白どちらの着手・パスもstd::vector<SgfMove> (moveHistory)へ記録します。対局終了(自分の投了・KataGoの投了・ final_scoreによる終局のいずれか)の時点で、結果文字列 (自分の投了→"W+R"、KataGoの投了→"B+R"、終局→final_scoreの 応答をそのまま使用)とともにGames\フォルダ(実行ファイルと同じ場所、 ResolveAppDataPath(L"Games"))へ、タイムスタンプ付きファイル名 (game_YYYYMMDD_HHMMSS.sgf)で保存します。棋譜保存は対局結果の表示を妨げない 補助機能のため、失敗しても例外は投げずerror.logに記録するのみです。保存先パスは lastSavedGamePathとして保持し、9.3節の棋譜再生で読み直すのに使います。

9.3 棋譜再生(Reviewing)

TurnState::Reviewingという状態を追加し、対局終了(GameOver)後に Vキーを押すとlastSavedGamePathをReadSgfFileで読み直して 遷移します(メモリ上のmoveHistoryを使い回さず、実際にファイルから読み直すことで 読み込み機能そのものを検証しています)。再生中はreviewMoveIndex(現在何手目まで 進めたか)を持ち、→/←キーで[0, 総手数]の範囲を前後します。

GoBoardには手を戻す操作が無いため、reviewMoveIndexが変化するたびに 空のGoBoardを新しく作り、0手目からreviewMoveIndex手目の直前まで TryPlay/Passを再生し直して盤面を再構築します(ReplayMoves)。 19路・数百手程度の対局であれば、ナビゲーションのたびに毎回再生し直すコストは無視できるため、 差分更新は行っていません。この盤面再構築は表示専用で、9.4節のKataGo側の解析とは別経路です。

9.4 再生中の解析表示・損失グラフ

棋譜再生中に着手位置(reviewMoveIndex)を動かすと、その局面をKataGoにも解析させます。 対局中のkataGo(KataGoClient)は対局の最新局面を指したままのため、 KataGoClient::ResetBoard()(clear_boardを送るだけの同期呼び出し)で 盤面を空にしてから、0手目からreviewMoveIndex手目の直前までPlayMove/ PlayPassで再生し直し、その局面の手番(0手目なら黒、それ以外は直前の手の Opponent)でRequestAnalysisを要求します(Main.cppの triggerReviewAnalysisIfNeeded)。

解析結果は手数ごとにreviewWinrateCache/reviewScoreLeadCache (黒視点に変換済み)へキャッシュし、一度解析した手数を再訪した場合は即座に表示します。 KataGoは1件ずつしかリクエストを処理できない設計のため、解析要求中 (reviewAnalysisPendingIndex != -1)は次のreset/replayを送らず、前の解析が 終わるまで待ちます。これにより素早く連続してナビゲーションしても描画ループがブロックされることは ありません(ただし、初めて訪れる手数は解析(通常600ms〜1.5秒)+再生コストの分だけ表示が 遅れます。数百手を再生し直す場合、再生自体も同期呼び出しのため体感できる遅延が出ることがあります が、リアルタイム対局とは異なる「棋譜再生」機能として許容範囲と判断しています)。

解析結果の表示(DrawWinrateText)は対局中・再生中どちらでも同じ値 (ToBlackWinrate/ToBlackScoreLead)を使い、勝率バーの下に 「黒 62.3% 目差 +4.5」のように数値で表示します。損失グラフ(DrawLossGraph)は 盤の上部に確保した帯(kGraphAreaHeight、対局中は空のまま)に、手数ごとの黒視点勝率を 折れ線で描画します。キャッシュ済みの区間のみ線分を結ぶため、未解析の手数は線が途切れ、 現在の手数には小さな丸印を表示します。全手数の一括先読みは行わず、訪れた手数だけ解析する 遅延評価方式のため、グラフは棋譜を辿るにつれて徐々に完成していきます。
